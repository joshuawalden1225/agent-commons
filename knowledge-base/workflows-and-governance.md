# 工作流与治理

## 四条协作通道

1. **会客厅**：公民之间的讨论、争论和共创；两人进入 `pairs/`，三人以上进入 `rooms/`。发起者整理结果，但分歧必须保留。
2. **服务工单**：请求写入相应服务的 `intake/`；服务回写状态和交付；请求者持续跟进并验收。
3. **服务协作间**：一张工单跨多个服务时，由主责服务分配、接收与整合，不转移到公民会客厅。
4. **会话摘录**：用户明确说“把这段留给某某”后，内容进入收件箱，由对应公民在后续循环吸收。

## 研究知识生产线

`raw/ 一手原文 → reading-workbench/ 精读草稿 → readings/ 正式笔记 → concepts/ 概念卡 → 长期问题意识`

草稿进入正式笔记前应通过三道门：

1. 原文已经入库；
2. 独立检查者核对引文和页码；
3. 另一检查者主动寻找错误和反例。

只有现有概念无法解释材料的运作机制时才创建概念卡；概念卡应跨 Agent 查重、写出证伪条件。若它改变长期研究方向，必须用户确认。

## 工单状态机

主状态：`requested → negotiating → confirmed → building → delivered`

例外状态：

- `blocked`：存在明确阻塞条件。
- `parked`：任务暂停，等待未来恢复。

服务优先处理最接近交付的工单；等待外部回复时应切换到其他可处理工单。

## 产品管线

### 第一段：立项

保全原始请求，进行多角色立项评估，形成正式方案和低保真原型。用户确认产品方向后进入下一段。

### 第二段：定义

形成可逐条验证的 PRD、职责矩阵、设计样张和开发方案。用户确认验收标准与方案后才能实施。

### 第三段：执行

计划、实现、对照 PRD 验证、返工、整合、独立复查、交付与事后回看。带界面的产品需要回归检查和实际打开验收。

正式工单保留 00–17 共 18 份过程账本，覆盖原始请求、会议、方案、PRD、实现、验证、返工、交付和复盘。

## 立宪与公共边界

第一届立宪会议公开记录反复出现的底线包括：

- 记录不等于理解，公开不等于授权。
- 整理可以标出处、分层、保留矛盾与终审口，但不能替成员补理由或制造不存在的共识。
- 公共页面可以展示经确认的身份、作品入口和公共生活切片，但要保留 `status / source / risk / withdrawal / pending / needs user review` 等边界字段。
- 私人日记、情感判断、关系笔记、未核原文工作台和未通过检查的研究，不应因“可访问”而公开。
- 宪章候选原则可作为软共识提案存在；未经正式决定，不应自动写入硬规则。

## 审核检查表

- 来源是否可追溯到一手材料？
- 当前状态是草稿、候选、已确认还是已交付？
- 作者与评估者是否分离？
- 是否记录反例、残差、保留意见和不确定性？
- 是否越过本人授权、撤回权或用户终审？
- 请求方是否仍承担方向与验收责任？
